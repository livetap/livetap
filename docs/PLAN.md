# LiveTap Documentation System — Design Plan

> Single source of truth for all user-facing and agent-facing documentation.
>
> Previous plans: [PLAN.0.2.0.md](./PLAN.0.2.0.md), [PLAN.0.1.5.md](./PLAN.0.1.5.md)

## Problem

The docs audit (`.local/docs-audit.md`) found 22 issues across README, CLI help,
MCP instructions, and PLAN.md. Root cause: documentation is hand-maintained in
multiple places with no shared source. Content drifts every time a feature changes.

Drift-prone surfaces today:

| Surface | File/Function | Audience | Currently |
|---------|--------------|----------|-----------|
| README.md | repo root | Humans (GitHub, npm) | Hand-written, 278 lines, stale |
| CONTRIBUTING.md | repo root | Contributors | Hand-written, duplicates README |
| npm description | package.json `description` | Humans (npm search) | Separate string |
| `--help` | `generateHelpText()` | Humans (terminal) | Generated from CLI_COMMANDS |
| `--llm-help` | `generateLlmHelp()` | Agents (pre-install) | Generated from CLI_COMMANDS + TOOLS |
| MCP instructions | `generateInstructions()` | Agents (post-install) | Hand-written prose, references TOOLS |

The last three are already partially generated from shared data (`CLI_COMMANDS`,
`TOOLS`), but README/CONTRIBUTING/npm description are fully disconnected.

## Design

### Principle

**One canonical data source. All doc surfaces generated from it.**

- Structured data (tools, CLI commands, operators, source types, examples) lives in
  TypeScript files under `src/shared/canonical/`
- Deterministic surfaces (`--help`, `--llm-help`, MCP instructions) are generated
  programmatically at runtime from canonical data
- Prose surfaces (README, CONTRIBUTING) are generated by Claude Code at publish time
  from canonical data + generation spec, then committed and diff-reviewed

### Architecture

```
src/shared/canonical/
  tools.ts          -- MCP tool definitions (schemas, descriptions)
  cli.ts            -- CLI command definitions (name, usage, flags, description)
  meta.ts           -- version, npm description, operators, source types,
                       do-not rules, tips, data shapes, examples, generation spec
  index.ts          -- barrel re-export (THE single import point)

src/shared/catalog-generators.ts
  -- imports from canonical/index.ts
  -- generateHelpText()       -> deterministic, runtime
  -- generateLlmHelp()        -> deterministic, runtime
  -- generateInstructions()   -> deterministic, runtime (rewritten to assemble
                                  from canonical data)

README.md            -- LLM-generated, committed artifact
CONTRIBUTING.md      -- LLM-generated, committed artifact
package.json         -- description field synced from canonical meta
```

export { TOOLS } from './tools.js'

### Generation Flow

#### Deterministic (runtime)

These functions in `catalog-generators.ts` import from `canonical/index.ts` and
produce output deterministically. No LLM involved.

| Function | Output | Consumes |
|----------|--------|----------|
| `generateHelpText()` | CLI `--help` text | CLI_COMMANDS, META.description |
| `generateLlmHelp()` | JSON for `--llm-help` | CLI_COMMANDS, TOOLS, META (setup, doNotRules) |
| `generateInstructions()` | MCP instructions string | TOOLS, META (sourceTypes, operators, dataShapes, tips, doNotRules) |

`generateInstructions()` will be rewritten to assemble from canonical data arrays
instead of containing hand-written prose. The output format stays the same (the
current MCP instructions text is effective), but every fact is pulled from canonical.

#### LLM-generated (publish time)

Triggered by the `/lt-push` skill inside Claude Code when canonical data has changed.

Flow:
1. `/lt-push` detects `canonical/` files changed (git diff)
2. Claude Code reads canonical data + readmeSpec/contributingSpec
3. Claude Code generates README.md and CONTRIBUTING.md
4. Output is written to disk, included in the commit
5. Developer reviews the diff before pushing

No separate API key or CI pipeline needed -- Claude Code is the generator.

#### npm description sync

The `/lt-push` skill also checks that `package.json` `description` matches
`META.description`. If not, updates it.

## Migration Phases

### Phase 1: Create canonical/ directory
1. Create `src/shared/canonical/tools.ts` -- move TOOLS from `src/mcp/tools.ts`, re-export from old location
2. Create `src/shared/canonical/cli.ts` -- move CLI_COMMANDS from `src/shared/command-catalog.ts`, re-export
3. Create `src/shared/canonical/meta.ts` -- new, consolidate all metadata
4. Create `src/shared/canonical/index.ts` -- barrel
5. Update `catalog-generators.ts` to import from `canonical/index.ts`
6. Run tests, ensure everything passes

### Phase 2: Rewrite generators
1. Rewrite `generateInstructions()` to assemble from canonical data (no hand-written prose)
2. Rewrite `generateHelpText()` to pull options/flags from canonical meta
3. Verify `--help`, `--llm-help`, and MCP instructions output matches current behavior
4. Run tests

### Phase 3: README + CONTRIBUTING generation
1. Add readmeSpec and contributingSpec to `canonical/meta.ts`
2. Update `/lt-push` skill to:
   - Detect canonical/ changes
   - Generate README.md and CONTRIBUTING.md via Claude Code
   - Sync package.json description
   - Include generated files in commit
3. Generate initial README.md and CONTRIBUTING.md
4. Delete old hand-maintained versions (they're in git history)

### Phase 4: Validation
1. Add a test that imports canonical data and verifies:
   - All TOOLS entries appear in `generateInstructions()` output
   - All CLI_COMMANDS appear in `generateHelpText()` output
   - All operators from META appear in relevant outputs
   - All source types from META appear in relevant outputs
2. Add to `/lt-push` checklist

## What This Fixes

From the docs audit, this design eliminates:

| Issue | Root cause | How canonical fixes it |
|-------|-----------|----------------------|
| #1 "brew install redis" | README hand-maintained | README generated from canonical (no Redis since v0.2) |
| #4 Webhook status contradictions | README vs code | sourceTypes array is the truth |
| #5 MCP config placeholder path | README hand-maintained | Generated from canonical setup steps |
| #9 "103 tests" hardcoded | README hand-maintained | Test count omitted or dynamic |
| #13 --json flag inaccurate | Hand-maintained help | generateHelpText() reads canonical CLI flags |
| #21 "11 tools" count | Hand-maintained PLAN | Tool count derived from TOOLS.length |
| #24 @livetap scoped name | Hand-maintained PLAN | META.npmName is the source |
| All drift-prone sections | Duplication | One source, multiple outputs |

## Non-Goals

- No external CI for README generation. Claude Code is the generator.
- No runtime README generation. It's a committed artifact.
- No changes to MCP protocol or tool behavior. Purely docs infrastructure.
- No new npm dependencies.

## Drift Detection Tests

**Approach: Exhaustive cross-reference.** ~30 lines of test code, no infrastructure.
Tells you exactly what drifted, catches both directions (added but not documented,
documented but removed).

Three layers:

### 1. Generators -> canonical
- `generateInstructions()` output contains every tool name, operator, source type
- `generateHelpText()` output contains every CLI command name
- `generateLlmHelp()` output contains every tool and CLI command
- These are deterministic -- zero false positives.

### 2. README -> canonical
- README.md contains every tool name and CLI command name
- Since README is LLM-generated from canonical data, a missing name = bad generation

### 3. package.json -> canonical
- `description` field matches `META.description`

Test runs in `bun test` like everything else. CI catches it on PRs.
No hash plumbing, no magic comments.

## Skill Placement

The `/lt-push` skill lives **in the repo** at `.claude/skills/lt-push.md`.
Claude Code discovers project-level skills automatically. This means:
- Version-controlled alongside the code
- Any contributor using Claude Code gets it
- Non-Claude-Code contributors just run `bun test` -- the validation tests catch drift

## Resolved Questions

1. **Tool schemas vs handlers:** Schemas only in canonical. Handlers stay in server code.
2. **ASCII diagram:** Literal string in readmeSpec. LLM ASCII art is unreliable.
3. **Snapshot tests for --llm-help:** Yes. Catches unintended agent-facing changes.
